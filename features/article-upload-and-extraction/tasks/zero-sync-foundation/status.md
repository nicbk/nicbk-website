## Notes carried into implementation

- **`/query` is the authorization boundary.** Zero has no permissions layer
  behind it. Scope by the `user_id` of a **server-derived context**, never from
  client arguments, and prove it non-vacuously with a second user's rows
  present.
- **Use Zero's current model, not the legacy one.** Synced queries + custom
  mutators; leave `ZERO_ENABLE_CRUD_MUTATIONS` false and do not pass
  `drizzle-zero`'s `--enable-legacy-mutators` / `--enable-legacy-queries`.
- **Three Postgres connections plus a replica volume**: `ZERO_UPSTREAM_DB`
  (direct, not pooled — it owns the replication slot), `ZERO_CVR_DB`,
  `ZERO_CHANGE_DB`, `ZERO_REPLICA_FILE`, `ZERO_ADMIN_PASSWORD`. Separate
  databases in the **existing** Postgres service, not a second service.
- **Exclude `pgboss` from the publication now**, while the publication is being
  defined, even though pg-boss does not arrive until task 4.
- **`zero/schema.ts` is generated with a CI drift check** — follow
  `scripts/gen-auth-schema.mjs`'s precedent rather than inventing a second
  pattern.
- **Follow the schema docs literally.** `article-core-schema.md` and
  `upload-jobs-schema.md` specify these tables column by column, including the
  pre-allocated-ID design where `upload_jobs.id` is the future article's ID.
  Deviating means re-deciding with the user, not improvising.
- **Separated type imports.** Everything here is server-only; a stray inline
  type import is how server modules reached the client bundle in #6.
- Re-verify current APIs before writing code (research-over-recall): Zero
  1.8.0, `drizzle-zero` 0.20.0. Both moved since the July research.

## What was built

- `zero-cache` (`rocicorp/zero:1.8.0`) in `docker-compose.yml`, single-node,
  on `app-internal`, with a persisted replica volume, a `/keepalive`
  healthcheck, a 10-minute start period and stop grace, and
  `depends_on: migrate` — it reads a publication a migration creates.
- `articles` and `upload_jobs` in `src/db/schema/lit-tracker.ts` and migration
  `0001`, with the generated `authors_search` column, its `pg_trgm` GIN index,
  the `uuidv7()` default, and the ownership cascades.
- `src/zero/schema.gen.ts`, generated by `drizzle-zero` from an explicit
  allowlist in `drizzle-zero.config.ts`, guarded by a new CI drift check.
- `src/zero/`: the context derivation, the query registry (`articles.mine`,
  `articles.byId`, `uploadJobs.mine`), the empty mutator registry, the Drizzle
  database provider, the API-key check, and both endpoint handlers.
- `/api/zero/query` and `/api/zero/mutate` route files wiring those handlers to
  the app's own session reader and configured keys.
- `src/db/schema.ts` became `src/db/schema/`: `identity.ts` (generated),
  `lit-tracker.ts`, and an `index.ts` barrel — so the generated file stays
  isolated from hand-written tables as #8–#11 add more.

## Decisions taken during implementation

Each of these departs from what the spec assumed, and each is recorded where a
future reader will meet it rather than only here.

- **Ownership columns are `text`, not `uuid`** — Better Auth's `user.id` is
  `text` and Postgres will not let a `uuid` FK reference it. Dated revisions in
  [article-core-schema.md](../../../../research/data-modeling/article-core-schema.md)
  and
  [upload-jobs-schema.md](../../../../research/data-modeling/upload-jobs-schema.md).
- **The publication is an explicit allowlist** (`zero_data FOR TABLE articles,
  upload_jobs`), agreed with the user. The spec only asked to exclude `pgboss`,
  which the default already does — the real exposure was Better Auth's
  `session` and `account` tables, whose rows carry session and OAuth tokens.
- **All three zero-cache connections point at the existing database**, agreed
  with the user, rather than at separate `cvr`/`change` databases. zero-cache
  namespaces that data into `zero_0/cvr` and `zero_0/cdc` schemas, it is the
  configuration Rocicorp's own single-node example uses, and separate databases
  could not be created by a Drizzle migration (no `CREATE DATABASE` inside a
  transaction) or by the image's init scripts (they only run on a fresh volume),
  so they would have needed hand-provisioning on nicbk-tower.
- **`X-Api-Key` on both endpoints**, with `ZERO_QUERY_API_KEY` and
  `ZERO_MUTATE_API_KEY` in `src/env.ts`. These are the only new variables the
  app itself reads; zero-cache's connection settings are Compose-level, like the
  existing `POSTGRES_*` ones.
- **Denying a read uses `.limit(0)`, not the documented empty `or()`**, which
  compiles to an invalid `WHERE ()` under server-side ZQL.
- **`articles.byId` exists although nothing calls it yet.** It is what makes
  "an argument naming another user's row still returns nothing" testable, which
  the task's testing.md requires; #9 is its first consumer.

## Verification

- Unit: 26 tests across `src/zero/` plus the extended `src/env.test.ts` —
  context derivation, the API-key check, every query's filter read off its AST,
  and both endpoints' 403/401/200 behavior against fabricated requests.
- Integration: 16 tests against real Postgres — migrations, defaults, the
  publication's contents, the generated column, the cascades, and cross-user
  isolation run through Zero's own `ZQLDatabase`. The isolation block includes a
  test asserting both users' rows are present and one asserting the *unscoped*
  query returns both, so a handler returning nothing could not pass.
- Drift: confirmed the new check catches a Drizzle schema change made without
  regenerating, and that the moved auth-schema check still passes.
- **Compose walkthrough** (`docker compose -f docker-compose.yml up -d --build`):
  `db` → `migrate` → `app` and `zero-cache`, with zero-cache healthy and holding
  an active replication slot (`zero_0_a`, `pgoutput`). A row inserted directly
  into Postgres appeared in the SQLite replica, and the replica contains
  **only** `articles` and `upload_jobs` — no identity tables. `/api/zero/query`
  answered 403 without a key and 401 with a key but no session. Plain
  `docker compose up --build` (dev override) came up the same way.
- One operational finding from that walkthrough, now in the README: `up`
  *without* `--build` after adding a migration leaves the migrator running from
  a stale image, so the publication does not exist and zero-cache crash-loops on
  `Unknown or invalid publications` until it does. It recovers by itself once
  the migration applies.
